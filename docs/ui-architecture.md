# UI prototype architecture

## Problem

Build the referenced three-panel desktop workspace and add local project persistence. Manual changes, approved AI resizes, and reopened projects must agree about selected dimensions, positions, and undo.

## Usage

Run `bun install`, then `bun run dev`. Use `bun run dev:web` for the renderer in a browser. `App` calls `useWorkspace()` and gives controlled views the selected object and intent callbacks. For example, a width field dispatches `{ kind: 'resize', dimension: 'width', valueMm }`; the sample approval dispatches `{ kind: 'apply-proposal' }`.

## Shape

- `electron/main.ts` owns window lifecycle, Go lifecycle, and two narrow IPC bridges: AI (`ai:propose-edit`) and project (`project:open`, `project:save`, `project:confirm-unsaved`, `project:set-dirty`). It owns native dialogs and safe atomic file access (temp file + rename); the renderer has no arbitrary filesystem access and stays sandboxed/isolated without Node integration.
- `src/workspace.ts` owns scene objects, selection, scene history, and proposals. Each object owns an absolute `positionMm` with X for width, Y for elevation, and Z for depth toward the front. Position is the local lower-left/back/bottom origin before rotation around the footprint center. Initial and added-object placement happens once. Millimeters are authoritative; display values convert at the UI boundary. The `load` action replaces the scene, resets history/revision/proposal, and restores selection — it is the only way projects are opened and it never mixes history between projects.
- `src/project.ts` owns the versioned `.renovacad` file format, validation, and limits. `src/App.tsx` builds/loads the `ProjectFile` and drives dirty tracking, save status, and photo embedding.
- `src/App.tsx` composes the inspector, viewport, and assistant. It owns camera, zoom, panel visibility, view mode, reference-photo data, project name/path, and dirty state. Reference photos are stored as `data:` URLs (base64) so reopening does not depend on a temporary `blob:` URL.
- `src/viewport.ts` owns the 26-entry camera registry, orbit limits, perspective and orthographic projection, and box geometry. It reads stored object positions. Projected polygons and extended grid segments are clipped against the camera's near plane.
- `src/components/KitchenPreview.tsx` projects the scene into SVG. It sorts visible faces by depth and renders selection and dimension labels. Pointer handlers distinguish a click from a drag before selecting or orbiting. Wheel zoom uses a non-passive listener so the page stays still.
- `src/components/ViewCube.tsx` projects a beveled cube using the current camera. Its six faces, twelve edges, and eight corners come from the same registry as camera presets and labels. The All views picker exposes hidden directions and keyboard access. One Home action resets the camera and fits the scene.
- `src/components/MoveControls.tsx` reads the selected object's coordinates and requests one-tile nudges. The reducer validates each complete 304.8 mm step within the ±10,000 mm coordinate bounds. Negative elevation is allowed; the preview does not enforce floor collisions.
- `src/styles.css` owns layout and visual tokens.

Every committed scene edit records a snapshot and invalidates pending proposals. Approval checks its scene revision and original target width. Selection, tabs, camera movements, projection, and panel visibility never consume undo. Numeric fields commit on blur or Enter and revert on Escape.

## Synthesis decision

The scene reducer provides one path for manual edits and approved sample changes. Controlled UI components read the same scene rather than keeping copies of dimensions. The local camera uses the existing scene model and requires no service, native bridge, or CAD engine.

## Tradeoffs and alternatives

We accept scene snapshots for a small memory-only prototype in exchange for straightforward undo. SVG projection gives the UI camera controls without adding a graphics engine. Its box geometry and depth sorting remain a preview; a future CAD renderer can replace KitchenPreview while keeping scene state and camera controls separate. Panel-owned scene state would duplicate dimensions, and a global store adds no useful capability yet.

## Implementation reconciliation

The reducer owns scene state, positions, selection, history, and proposals. Tabs, settings, notices, camera, frame, zoom, panel visibility, project path/dirty, reference-photo `data:` URLs, and measure points (temporary) remain presentation state. The `load` action initializes the workspace consistently; opening a project never mixes history between projects. Measure points are not persisted. Export and cloud are out of scope.

**Project persistence (this milestone):** `src/project.ts` defines `ProjectFile` version 1, validation, and limits (12 MB file, 5 MB photo, 50 objects). The saved file preserves version, name, all scene objects (IDs/kinds/dims mm/positions/rotations), selected ID, settings (`unit`, `showGrid`), camera (`yaw`/`pitch`/`projection`/`zoom`), view mode, and the reference photo (`name`, `mimeType`, `dataUrl`). Not persisted: API keys, tokens, pending proposals, transient errors, in-flight requests, or undo history. Loading validates at the boundary and rejects unsupported versions, malformed JSON, invalid scene values, or bad assets with a helpful message while leaving the current project intact. Canceled dialogs and failed writes also leave the current project intact and show an actionable error. Photo import reads via `FileReader.readAsDataURL`; the `data:` URL is displayed directly and persisted, so no `blob:` URL is needed to reopen. Approved AI resizes commit as normal scene edits and persist like any other edit.

**Single file vs. folder:** a single portable `.renovacad` JSON file was chosen for the current demo — one file to choose, move, or email, no broken references for a single embedded image, and trivial atomic save (temp-file + rename). A project folder with sidecar assets was considered; it would add complexity for the current image sizes (≤5 MB) and demo needs, and could be revisited if assets grow.

**Security and save safety:** the renderer stays sandboxed/isolated without Node; `electron/preload.ts` exposes only `window.renovacadProject` with `openProject`, `saveProject`, `confirmUnsaved`, `setDirty`, `confirmClose`, and a quit-save event — no arbitrary filesystem access, no `fs` in the renderer. Baseten credentials stay in the Go backend; the renderer never sees `BASETEN_API_KEY` or the per-launch token. Saves use an atomic temp-file + rename so a partially written file never replaces the last good project; on non-POSIX filesystems this is best-effort but the previous file is preserved on failure. `browser-only dev:web` has no native bridge and shows an honest “not available in browser preview” message. Unsaved changes warn before New/Open/Quit (native Save/Discard/Cancel dialog) and `beforeunload` guards refresh/close; cancellation keeps the current project. Save status is shown in header (“Not yet saved” for untitled never-saved workspace, otherwise Saved/Unsaved/Saving) and footer (Saved/Unsaved/Saving/Error vs Not yet saved) with errors and unsaved changes always easy to notice; the header keeps one primary Save button, Save As lives with a clear label in Workspace settings (and via Save when no file exists) — no duplicate save icons. Save updates the current project, Save As creates a separately chosen file.

**What remains a preview:** the 3D view is a local SVG projection of rectangular objects, not a CAD engine; grid and AI Render placeholders will evolve. This distinction is preserved in the badge (“3D preview — not a CAD engine”) and documentation.

Numeric edits normalize to 0.001 mm and ignore unchanged display values, preserving proposals and redo after a field is focused and blurred. The sample resize cannot create an empty change at the maximum width. Clicks and tool shortcuts share one handler. Tabs use arrow keys, Home, and End. Text entry, native selects, and composition input do not trigger design shortcuts.

Focus mode hides both side panels while preserving their individual visibility preferences. The hidden panels retain their state. Fit updates the frame and resets zoom at the current angle. Home also restores the Top Front Right perspective. Additions and restored objects trigger a fit once. Movement, movement undo/redo, dimensions, rotation, selection, and grid visibility preserve the frame, so translation remains visible against the world grid.

Floor lines are spaced by `TILE_MM`, independently of object bounds. Grid drawing bounds never enter camera fitting. Move mode adds a noninteractive vertical reference plane oriented toward the camera and a height-to-floor guide. The grid toggle hides both lattices while retaining the selected object's height guide.

The toolbar catalog is the sole object-creation location. The cube is the orientation location. The viewport owns grid visibility; the zoom percentage is read-only. Numeric properties and the object list remain because they serve different tasks.
**Viewport interactions (this milestone):** lower-left axis indicator now three arrows (X red #ff453a, Y green #30d158, Z blue #0a84ff) with labels at tips, derived from same camera projection as viewport via `axisScreenVectors` (verified signs against `createProjector` raw math for front/top/home/perspective/orthographic); arrows update as you orbit, and when projection is very short (<0.18) handle clearly as a dot (filled if toward viewer, ring if away) with offset label — tested for front Z short, top Y short, and perspective/orthographic sign consistency. Keep view cube separate. Move drags selected cabinet/sink in X/Z at current Y via worldDeltaFromScreenDelta (2x2 basis from projector), one move-to commit = one undo, cancels cleanly, invalidates proposals, marks dirty. Plane fallback checks |dir.y|>0.12 else disables drag. Snapping aligns axis-aligned edges within 40mm via snapDelta with guides, Shift bypasses; rotated snapping unsupported. Measurement uses crosshair and worldPointOnPlane (floor Y=0 or object top), distanceMm, HUD with Back/Clear/Esc, temporary not saved. Annotate remains placeholder. Photo analysis in Photo view has explicit Analyze button with consent notice, validates type/size before sending only the photo, handles errors/timeouts, shows labeled description + follow-up questions, does not auto-modify scene, keeps editing/saving usable when provider down.

**Photo-to-layout draft (this milestone):** Photo view now offers **Create draft layout** (explicit, beside Analyze) with consent “sends only this photo to Baseten … approximate — please measure … current scene preserved until you apply.” No auto-send on import; both actions validate mime/size strictly before any network. Draft response is versioned (`version:1`) and limited to `base-cabinet|wall-cabinet|tall-cabinet|wall|sink` with `dimensionsMm`/`positionMm`/`rotationDegrees` (all mm, rounded 0.001, limits 25.4–10000, ±10000 positions, 1–8 objects). Backend enforces via `layout.Service` and `baseten.Client.ProposeLayout` (vision `image_url` data URL, `response_format json_object`, 1200 tokens); frontend revalidates before dispatch. `needs_info` (blurry / not kitchen) returns `message` + questions instead of inventing objects. Review UI shows description, warnings (“Approximate dimensions — please verify”), approximate note, follow-up questions, object list with editable Name/Width/Height/Depth/X/Y/Z/Rotation inputs and Remove per object, and explicit “Apply draft — add N objects (existing kept)” vs Cancel. Apply uses `workspaceReducer` `apply-layout` which appends objects in **one** `commit` (one undo, stable `crypto.randomUUID` IDs, mm) — do not replace existing design silently; note explains Add vs Replace (this milestone adds). Revalidation before apply caps at 50 total objects; invalid draft aborts with message. Late responses after photo/project switch are discarded via `layoutReqId` + captured photo identity + `projectGenerationRef` bump on `applyProjectFile` (also covers analyze). Save/project-switch race fixed via `projectGenerationRef` epoch: saves capture `initiatingGeneration`/`initiatingPath`; after await only `setProjectPath` if generation unchanged, preserving new project’s path and allowing later Save of new project to succeed; `isDirty`/`isSaving` use refs + `pendingSavesRef` for overlapping saves. All via narrow `window.renovacadApi.proposeLayout` bridge; keys never reach renderer. Draft objects save/reopen via existing `ProjectFile` scene (standard objects) — no format bump needed, existing `.renovacad` files remain compatible.

**What the draft can and cannot infer:** Can recognize clearly visible base/upper/tall cabinets, sink, walls and approximate positions along walls using catalog defaults (mm) when photo lacks measurements. Cannot provide verified construction-ready dimensions from a single photo — all dimensions are marked approximate/default and require user measurement; wall lengths, ceiling height, appliance models beyond sink placeholder, material specifics, and depth beyond defaults are not reliably inferable and are surfaced as follow-up questions. Photo-to-layout never auto-measures; user must edit before applying.
